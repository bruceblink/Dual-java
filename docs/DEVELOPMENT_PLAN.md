# Dual Demo 与正式游戏开发计划

## 项目定位

- 当前仓库 `Dual` 定位为**可运行玩法演示**。它保留 Java + Processing 客户端和 Java TCP Relay，用于验证操作手感、规则和视觉方向。
- 正式游戏不在本仓库内渐进迁移，也不复用现有 Java 网络代码；它从干净的协议和工程边界开始实现。
- 当前仓库只接受演示版本必要的缺陷修复、玩法验证和文档维护，不再承担 Android、正式联机或服务端演进。

## 正式游戏架构

正式游戏采用以下组合：

- 客户端：Godot 4 + GDScript，发布 Windows、macOS、Linux 与 Android。
- 服务端：Go 1.26，独立仓库、Docker 部署、WebSocket Secure（WSS）连接。
- 联机模型：服务端权威。服务端维护比赛状态，客户端只发送操作并渲染服务端确认的状态。

详细的备选方案、边界和原型验收见 [技术选型评估](TECHNOLOGY_EVALUATION.md)。

## Demo 基线

- 现有客户端是 Java 21 + Processing；当前 `server` 是同一 Gradle 多模块工程中的 Java TCP Relay。
- Relay 只转发输入，按连接到达顺序配对，不维护可加入的房间，也不维护比赛状态。
- 当前联机只同步最新输入；它不足以保证网络抖动下两端的模拟结果一致。
- 已完成的本地改进包括联机输入镜像、连接与握手超时、断线处理，以及武器操作反馈。
- 这些实现是玩法和网络风险的参考样本，不是正式版本的代码基线。

## 正式游戏第一阶段：技术验证

1. 建立独立工程
   - 创建 `dual-game-client`（Godot）和 `dual-game-server`（Go）两个独立仓库，各自拥有版本、CI 和发布节奏。
   - 从第一天起使用版本化 WSS 协议；不需要兼容 Demo 的裸 TCP 报文。
   - 验收：客户端可以独立导出桌面构建，服务端可以独立构建 Docker 镜像，双方使用协议 v1 完成连接。

2. Godot 客户端原型
   - 建立固定 640 x 640 的 2D 场景，完成角色移动、短弓、长弓蓄力与碰撞的最小闭环。
   - 同时实现键盘和触摸控制；触摸控制必须能移动、瞄准、短射和长弓蓄力。
   - 验收：桌面可运行，并能导出且在 Android 真机上完成一局本地人机对战。

3. Go 服务端原型
   - 在独立 `dual-game-server` 仓库中提供 WSS 连接、显式房间码、双人配对和健康检查。
   - 每个房间运行固定 60 Hz 模拟循环；输入经过序号、频率和数值范围校验后才进入模拟。
   - 验收：`go test ./...`、`go test -race ./...` 和 Linux 静态二进制构建通过；两个测试客户端能完成建房、加入、断线和结算。

4. 联调垂直切片
   - Godot 客户端通过 WSS 与 Go 服务端进行一局双人对战。
   - 服务端按固定频率下发状态快照；客户端只对本地移动做短暂预测，并以快照纠偏。
   - 验收：可注入延迟、短暂丢包和乱序输入，双方都能看到相同胜负结果或明确的中断结果。

## 正式游戏第二阶段：实现

1. 在新工程重新实现核心玩法：移动、箭矢、碰撞、伤害、胜负与再战。
2. 在新工程重新实现表现层：粒子、屏幕震动、菜单、房间和断线反馈。
3. 完成桌面安装包、Android 签名 APK/AAB、服务器镜像和部署说明。
4. Demo 保持冻结并可运行，不删除其 Java Relay，也不与正式服务端长期互通。

## 质量门槛

- 服务端：每次变更运行单元测试、竞争检测和协议兼容测试；合并前必须通过容器构建。
- 客户端：核心规则有自动化测试；每个发布候选在桌面和 Android 真机完成冒烟测试。
- 协议：每条消息有版本、长度和字段定义；兼容性变更必须先更新规范和双方测试。
- 发布：客户端与服务端独立版本、独立 CI 和独立发布节奏，不再由同一个 Gradle 构建驱动。

## 否决条件

- 若 Godot 原型无法在目标 Android 设备稳定运行，或触摸操作不能达到可玩水平，则停止 Godot 迁移，改做 Kotlin + libGDX 原型后再选型。
- 若 60 Hz 权威模拟在目标服务器配置上无法稳定支撑预期并发，则先优化房间循环与消息格式，不在客户端恢复 P2P 锁步作为规避手段。
